# GEO Audit & Recommendations — pj-web (rahendarosmedi.com)

Audit date: 2026-10-09. Scope: static repo inspection only (Jekyll source), no build was run.

## 1. Stack summary

- **Generator**: Jekyll (Ruby static site generator), theme is a customized Ghost/Casper-style layout (`_layouts/`, `_includes/`). Fully server-rendered static HTML — no client-side framework renders page content, which is good for GEO (see §3.6).
- **Hosting/CI**: GitHub Pages via GitHub Actions (`.github/workflows/jekyll.yml`), custom domain `rahendarosmedi.com` (`CNAME`).
- **Content**: homepage (`index.html`), one about page (`common/about.md`), one blog post (`_posts/2022-12-25-identites-communautes-imaginees.md`), author archive pages generated by `jekyll-auto-authors` (`_layouts/author-page.html` + `_data/authors.yml`), tag pages (`_layouts/tag.html`), RSS feed (`common/feed.xml`).
- **Config**: `_config.yml`, `Gemfile`.

## 2. Current GEO posture — what's already good

- `robots.txt` already explicitly allows the major AI crawlers (`GPTBot`, `ChatGPT-User`, `ClaudeBot`, `anthropic-ai`, `PerplexityBot`, `Perplexity-User`, `Google-Extended`, `Bingbot`) plus a wildcard `Allow: /`, and points to a sitemap. This is already aligned with current bot-naming conventions ( [the GPTBot/ChatGPT-User user-agent names come from OpenAI's own bot documentation](https://platform.openai.com/docs/bots) , [ClaudeBot/anthropic-ai are documented by Anthropic](https://support.anthropic.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler) , [PerplexityBot/Perplexity-User are documented by Perplexity](https://docs.perplexity.ai/guides/bots) , and [Google-Extended is Google's AI-training-specific token, separate from Googlebot](https://developers.google.com/search/docs/crawling-indexing/overview-google-crawlers#google-extended) ).
- Canonical URLs are emitted on every page via `<link rel="canonical" href="{{ page.url | absolute_url }}" />` in `_includes/head.html:2`, which is the mechanism search/AI crawlers expect for [duplicate-content consolidation](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).
- Basic JSON-LD already exists in `_includes/head.html`: a `WebSite` block for generic pages and a `BlogPosting` block (with `author`, `publisher`, `datePublished`/`dateModified`) for posts, using the [schema.org vocabulary](https://schema.org/BlogPosting).
- Content is 100% static HTML/Markdown rendered at build time — there is no JS-gated rendering of article text, so crawlers that don't execute JavaScript (most AI crawlers, including GPTBot) can read everything. This is a structural strength worth preserving as the site grows.
- A real, substantive bio already exists in `common/about.md` (career history: semiconductor manufacturing → DevOps/network engineering → product management → Paris 2024 Olympics telecom infra → business development for enterprise APIs). This is good raw material for GEO — it just isn't exposed in a machine-retrievable format yet (see §3.1/§3.2).
- `jekyll-sitemap` is declared in `_config.yml`'s `plugins:` list, and `robots.txt` correctly references `https://rahendarosmedi.com/sitemap.xml`.

## 3. Gaps and recommendations (prioritized)

### HIGH impact

**3.1 — No `llms.txt` exists.** There is no file matching `llms.txt` anywhere in the repo. [`llms.txt` is an emerging convention — a concise Markdown index placed at a site's root (`/llms.txt`) that gives LLMs a curated, link-based summary of a site instead of making them parse HTML](https://llmstxt.org/). Drafted in this task at `dev-geo-optim/profile-md-files/llms.txt` — needs to be copied to the Jekyll root (see `dev-geo-optim/profile-md-files/README.md` for exact placement) so it builds to `https://rahendarosmedi.com/llms.txt`.

**3.2 — The real bio in `common/about.md` is not citation-ready or structured for extraction.** It's a single run of prose with no explicit dates for career transitions, no clear "fact" sentences (e.g., no explicit statement "X is a Product Manager based in Paris, France" that an LLM could lift verbatim), and no structured data tying it to a `Person` entity. Recommendation: add a `Person` JSON-LD block to the about-page template (or a dedicated include loaded only on `permalink: about.html`) with `name`, `jobTitle`, `worksFor`/`description`, `url`, and `sameAs` (the social links already captured in `_config.yml:76-83`). See [schema.org `Person`](https://schema.org/Person) and [schema.org `Organization`](https://schema.org/Organization) if a company entity is ever added. This is also what the drafted `dev-geo-optim/profile-md-files/about.md` externalizes as a directly-fetchable alternative.

**3.3 — Identity/name inconsistency across the codebase actively hurts entity resolution.** Three different names are used for what appears to be the same person, with no `sameAs` linking them in rendered HTML:
  - `_config.yml:44` → `author.name: Biloute`
  - `_data/authors.yml:3` → `name: Rahenda` (used on `/author/rahenda/` via `_layouts/author-page.html` and on post bylines via `_layouts/post.html:29`)
  - `_config.yml:75` (orphaned `ai_visible_content.entity.name`) → `"Biloute R."`
  - Domain is `rahendarosmedi.com`, GitHub handles are both `biloute00` and `rahendatri` (`_config.yml:46` and `:80-82`).
  An LLM trying to answer "who runs rahendarosmedi.com" has no single consistent name to anchor on, and no explicit statement that "Biloute" and "Rahenda" are the same person. Fix: pick one canonical display name, use it consistently in `_data/authors.yml`, `_config.yml:author.name`, and the new profile files, and if both names are intentionally used (e.g., pen name vs. real name), state that explicitly in `about.md`/`llms.txt` (e.g., "also known as / writes under the name …") so it becomes a citable fact rather than an unexplained contradiction.

**3.4 — `_data/authors.yml:6` has a literal placeholder bio: `bio: "{ }"`.** This string renders verbatim on the live `/author/rahenda/` page (`_layouts/author-page.html:34`, `<h2 class="author-bio">{{ author[1].bio }}</h2>`) — i.e., production currently serves `{ }` as the author's bio to every crawler and visitor. Also `_data/authors.yml:4` location (`Rennes, FR`) conflicts with `_config.yml:45` (`Paris, FR`). Fix immediately: replace with a real one-paragraph bio (can be sourced/condensed from `common/about.md`) and reconcile the location.

**3.5 — The orphaned `ai_visible_content` config block in `_config.yml:73-83` is dead configuration that renders nothing.** The commit history shows `jekyll-ai-visible-content` was added to `Gemfile` and `plugins:` (commit `2f9879c`) then removed from both in the very next commit (`a816af1`), while the `ai_visible_content:` data block was left behind — and its `job_title`/`description` fields were simultaneously blanked out to `""`. No template in `_includes/` or `_layouts/` reads `site.ai_visible_content` (confirmed via full-repo grep), so this data is currently inert — it neither builds a page nor injects meta tags. Recommendation: either (a) delete the dead block to avoid confusing future maintainers, or (b) repurpose its values (they already contain the right `sameAs` links) to hand-populate the `Person` JSON-LD from §3.2 and the new `llms.txt`/`about.md` files, since the plugin itself is not installed.

**3.6 — The single blog post is excluded from every discovery surface.** `_posts/2022-12-25-identites-communautes-imaginees.md` has `unlisted: true` and `sitemap: false` in its front matter. `unlisted: true` makes `_includes/loop.html:19` (`{% unless post.unlisted %}`) skip it on the homepage, `common/feed.xml:9` (`{% unless post.link or post.unlisted %}`) skip it in RSS, and `sitemap: false` excludes it from the generated `sitemap.xml`. Net effect: the site currently has **zero discoverable content pages** besides the homepage shell and the about page — there is nothing for an AI crawler to index or cite beyond a generic bio. If this post (or future posts) is meant to be public, remove `unlisted: true`/`sitemap: false`; if it's intentionally private, the GEO priority becomes **publishing new, citable content**, since an LLM can't retrieve or cite what isn't crawlable.

### MEDIUM impact

**3.7 — No `Person`/`Organization` JSON-LD anywhere, only `WebSite`/`BlogPosting`.** `_includes/head.html:20-42` emits `Person` only nested inside a post's `author` field (name + url, no `jobTitle`, `image`, or `sameAs`). Add a standalone top-level `Person` JSON-LD (ideally on the homepage and the about page) per [schema.org `Person`](https://schema.org/Person), including `sameAs` pointing at the LinkedIn/GitHub/GitLab profiles already listed in `_config.yml:76-83`. This directly helps LLMs build a confident "knowledge panel"-style entity for the site owner.

**3.8 — `<html>` has no `lang` attribute.** `_layouts/default.html:2` is `<html>` with no `lang`. Only `common/404.html:8-9` sets `lang="en"` (and the site's actual content, e.g. the one post, is in French per `_config.yml:29` `locale: fr`). Add `lang="{{ site.locale | default: 'en' }}"` (or hardcode `fr`) to `_layouts/default.html` — language signaling affects both accessibility and how LLM crawlers classify/route content for retrieval. Also consider an `og:locale` meta tag in `_includes/head.html` per the [Open Graph protocol](https://ogp.me/).

**3.9 — Broken forward-looking link on the homepage.** `index.html:19` links to `/tutorials/` (`career-ops tutorial`) with an inline comment `<!-- TODO: point href at the new page once it exists -->` — this page does not exist in the repo, so it 404s today for both humans and crawlers. Either remove the link until the page ships, or gate it behind a feature flag, since a crawled 404 from the homepage is a small but avoidable trust signal issue.

**3.10 — `_config.yml:80-82` includes a non-functional placeholder: `url: test@mail.mail`** under `author.links` (rendered nowhere currently, but a trap for future templates that do consume `site.author.links`). Replace with a real contact method (or remove) before any template starts surfacing it, so a future "contact" block doesn't publish a fake address as fact.

**3.11 — Verify `jekyll-sitemap` is actually bundled.** It's listed in `_config.yml`'s `plugins:` but **not** explicitly in `Gemfile`'s `:jekyll_plugins` group (only `jekyll-feed`, `github-pages`, `liquid_reading_time`, `jekyll-paginate-v2`, `jekyll-auto-authors`, `jekyll-include-cache`, `jekyll-github-metadata` are listed). It likely resolves transitively because `github-pages` bundles the [GitHub Pages–approved plugin whitelist](https://pages.github.com/versions/) which includes `jekyll-sitemap`, but since this repo builds via a plain `bundle exec jekyll build` in GitHub Actions (`.github/workflows/jekyll.yml:41`) rather than GitHub's native Pages build, it's worth confirming `sitemap.xml` is actually produced in `_site/` after a build — if the gem isn't resolved, the `Sitemap:` line in `robots.txt:28` points at a 404.

### LOW impact

**3.12 — No `FAQPage` schema** — not currently needed since there's no FAQ content, but if an FAQ section is added to the about page or a new page, structured `FAQPage` markup ([schema.org `FAQPage`](https://schema.org/FAQPage)) is a high-value, low-effort addition for direct-answer retrieval by AI assistants.

**3.13 — Protocol-relative third-party asset URLs** (`//fonts.googleapis.com/...`, `//cdnjs.cloudflare.com/...` in `_layouts/default.html:21-24`) are legacy syntax; not a GEO blocker (these don't gate content rendering) but worth modernizing to `https://` for consistency during any future template cleanup.

**3.14 — `short_url: 'rahendablog.github.io/'`** in `_config.yml:32` is stale (the site now uses the `rahendarosmedi.com` custom domain per `CNAME`) and isn't referenced by any template today (confirmed via grep) — low risk, but worth removing so nobody wires it into a future canonical/alternate-URL tag and creates a mismatched domain signal.

## 4. Suggested execution order

1. Fix the literal `{ }` author bio and name/location inconsistency (§3.3, §3.4) — currently live, embarrassing, and cheap to fix.
2. Decide the fate of the unlisted/unsitemapped post and the publishing cadence for new content (§3.6) — without indexable content, no other GEO work moves the needle.
3. Ship `llms.txt` and the profile markdown (§3.1/§3.2) — drafted under `dev-geo-optim/profile-md-files/`, ready to promote to the site root per that folder's `README.md`.
4. Add `Person` JSON-LD + `lang` attribute (§3.7, §3.8).
5. Clean up dead config and placeholder links (§3.5, §3.9, §3.10, §3.14).
6. Confirm sitemap generation end-to-end (§3.11).
